Goals & Constraints

The sprint targeted three focus areas across the Obsidian plugin's delivery and user experience.

Identify concrete improvements in alternative notification channels, UX interactions, and temporal logic for deadlines.

Minimal to moderate — no external infrastructure. Works within Obsidian Plugin API limits.

2–8 weeks total, with features shippable incrementally in plugin-sized iterations.

Mobile-compatible, no persistent background processes beyond setInterval, single Telegram API transport.

SCAMPER Brainstorming

16 actionable ideas produced across all 7 dimensions, each mapped to a focus area.

S
Substitute — What could be replaced?
Channel
S-1
Webhook Relay Alternative
Replace hard dependency on Telegram with a configurable webhook URL so notifications can be sent to Discord, Slack, n8n, or a custom endpoint using the same templating engine.
S-2
OS Native Notification Fallback
Substitute Telegram with Obsidian's built-in Notification API as a zero-setup fallback channel when no bot token is configured.
C
Combine — What could merge?
Channel UX
C-1
Inline Action Buttons
Combine outgoing reminder messages with interactive Telegram reply buttons (Snooze 1h, Mark Done, Dismiss) so the user can act without opening Obsidian.
C-2
Obsidian Reminders Plugin Bridge
Combine with the community Reminders plugin by reading its data, avoiding duplicate task scanning and leveraging its existing scheduled-task index.
A
Adapt — Cross-field borrowing
UX Temporal
A-1
Email-Style Snooze Patterns
Adapt Gmail/Outlook snooze logic: configurable presets (1h, tomorrow 9am, next week) that store a snoozedUntil timestamp or rewrite the inline deadline.
A-2
Priority Inbox Adaptation
Adapt the "priority inbox" pattern: rank due tasks by composite score (deadline proximity + file recency + custom priority frontmatter) so only the top N items notify.
M
Modify — Magnify / Minify / Scale
UX Temporal
M-1
Context-Rich Notifications
Magnify Telegram messages to include a 2-sentence context block (extracted from the note body) plus a direct obsidian://open?file= deep link.
M-2
Dynamic Check Cadence
Modify the fixed interval to a per-urgency schedule: every 30 min normally, every 5 min within 1h of a deadline, once daily for distant tasks.
M-3
Dedicated Sidebar View
Magnify plugin visibility with a custom sidebar panel showing next reminders, snoozed, and overdue tasks. Click opens the file and scrolls to the task. Quick filters: today / week / tag.
P
Put to Another Use— Repurpose the mechanism
Channel UX
P-1
Habit Tracker Nudges
Repurpose the reminder engine to send recurring daily/weekly habit nudges sourced from a dedicated #habit tag, unrelated to deadlines.
P-2
Telegram as Ingestion Inbox
Reverse-use the bot: allow users to send messages to the bot, which appends them as tasks to a configurable daily note in Obsidian.
E
Eliminate — Strip away friction
UX Temporal
E-1
Frictionless Bot Pairing
Eliminate manual token/ChatID copy-paste by generating a QR code in settings that deeplinks to a Telegram auth flow or BotFather-like setup wizard.
E-2
Smart Duplicate Suppression
Eliminate repeated notifications for the same overdue task by defaulting to a "notify once per day" policy rather than every check cycle.
R
Reverse — Flip the flow
Channel Temporal
R-1
Pull-Based Task Query
Reverse the push model: let the user message the Telegram bot /today to receive the current due-task list on demand instead of relying solely on scheduled pushes.
R-2
Anticipatory Early Warnings
Reverse the "notify at deadline" logic: send early warnings at configurable advance intervals (1 day before, 1 hour before) shifting from reactive to proactive.
R-3
Reminder-First Authoring
Reverse the workflow: command "Create task with reminder" opens a guided modal (text, date, destination file) that writes the task inline. Lowers entry barrier for new users who don't know the task syntax.

Strategic Recommendation

💡 Innovation Insights

The most powerful breakthrough was inverting the notification flow from reactive → proactive (R-2). This transforms a "deadline alarm" into a "planning assistant," arguably changing the plugin's value proposition more than any single feature. Equally unexpected was discovering that Obsidian's limited mobile process lifetime became the plugin's strongest safeguard — ideas requiring bi-directional Telegram polling all cluster at the bottom of the ICE ranking, showing the path forward is smarter push scheduling rather than fighting platform limits. Finally, the webhook abstraction (S-1) proved to be a multiplicative feature: not just a Telegram alternative, but a universal notification adapter.

Phase 1 Strategy: Begin with E-2 and R-2 to solve immediate pain (notification spam & missed deadlines) while building temporal infrastructure that A-1 will later reuse.

Phase 2 Strategy: Layer M-1 (context blocks + deep links) and A-1 (snooze). Both reuse Phase 1 scheduling logic and together create a "smart inbox" feeling.

Phase 3 Strategy: Ship S-1 (webhook decoupling) and M-2 (dynamic cadence). Webhook expands addressable user base; cadence optimizes battery and API usage when paired with webhook delivery.

Risk Mitigation for Low-Confidence: Build getUpdates polling as an off-by-default experimental toggle. Validate the mechanism without destabilizing the push-only core. If adoption is low or battery complaints arise, it remains opt-in without regressing stability.

🎯 Integrated Recommendation

"Smart Reminder Platform" — R-2 + M-1 + A-1 + S-1

The plugin evolves from a single-channel deadline pusher into an intelligent, multi-channel reminder system. Users configure advance-warning windows (R-2), and each notification carries rich task context with a direct Obsidian deep link (M-1). When a reminder fires, users can snooze it with preset options that skip checking until the chosen time (A-1). Power users replace Telegram with any webhook endpoint — Slack, Discord, n8n, custom — making the plugin agnostic to delivery channel (S-1). The temporal engine (advance warnings + snooze) and universal transport (webhook templates) are the two pillars.

💰 Resource Allocation

  • Phase 1 (Weeks 1–2): ~20% effort — temporal infrastructure, anti-spam filter. Reuse existing scan logic.
  • Phase 2 (Weeks 3–5): ~35% effort — context extraction, snooze state management, settings UI.
  • Phase 3 (Weeks 6–8): ~35% effort — webhook transport abstraction, dynamic interval logic, template compatibility layer.
  • Experimental (TBD): ~10% buffer — polling infrastructure for C-1 / P-2 / R-1 if telemetry validates demand.

🚀 MVP / Downgraded Compromise

"Essential Deadline Intelligence" — R-2 + E-2 + M-1 (light)

Shippable in ~1 week. Add configurable early-warning intervals (1 day, 1 hour) to the existing daily check loop. Deduplicate notifications per task per calendar day. Append a single obsidian://open link in Telegram messages. This MVP does not include snooze or webhook replacement, but immediately demonstrates the plugin becoming smarter not just bigger. Path to full solution: add snooze controls once users request it, then introduce webhook transport once channel-diversity requests accumulate.

🗑️ Appendix: Considered but Excluded

P-1 Habit Tracker Nudges — Off-target: habit tracking is a separate product category outside the scoped innovation areas (Telegram alternatives, UX, temporal logic). Would compete with dedicated habit plugins and dilute the plugin's core identity.
Oracle Second Opinion

Adversarial Review:
Where the Plan Is Wrong

A senior product strategist stress-tests the SCAMPER plan for hidden assumptions, optimistic effort estimates, and missed risks.

Verdict: Directionally sound but dangerously optimistic on effort, systematically underscoring bi-directional Telegram features behind an unvalidated mobile constraint, and overlooking a looming UX complexity catastrophe from stacking temporal features without mental-model governance.

!

🔥 High Severity Critiques

🔥 Overstated Confidence

R-2 — Anticipatory Early Warnings (Original ICE 576)

Original: 576 (8×9×8) → Oracle: 288 (8×6×6) −288

Confidence 9 is unjustified. No evidence users want advance notifications — the plugin's value prop is "notify when due." A user with 30 tasks gets 60 notifications (30 early + 30 actual). The existing maxTasksPerCheck: 10 proves the authors already know volume is a problem. R-2 amplifies the exact pain E-2 tries to solve.

Ease 8 → 6: notifiedTasks needs a new dimension — not just "was notified" but "which warning level was sent." Schema migration for existing state.

🔥 Scope Underestimation

E-2 — Smart Duplicate Suppression (Original ICE 567)

Original: 567 (7×9×9) → Oracle: 378 (7×9×6) −189

"Near trivial" masks real complexity. What is a "calendar day"? A user in Tokyo flies to New York — their day shifts 13 hours. Do you track UTC day? Local device day? The current key notified:${task.id}:${deadlineDate} needs date-component semantics and explicit timezone policy. Requires testing across date boundaries and likely a settings toggle.

🔥 Phantom Constraint

C-1, P-2, R-1 — Bi-Directional Telegram (Original ICE 60–96, Conditional)

Original: 60–96 (Conditional) → Oracle: 180–320 (Desktop viable) +120 to +224

The report dismisses all three because "getUpdates polling only works while Obsidian is active." This conflates mobile background limits with desktop reality. Power users — the target market — are on desktop. A 30-second HTTP poll with offset is trivial; the plugin already runs a check loop.

C-1 re-score: ICE ~320 (8×6×7) desktop-only, experimental toggle. R-1 re-score: ICE ~280 (6×6×8). These should be Phase 2 for desktop users, not buried.

🔥 Hidden Dependency

A-1 — Email-Style Snooze (Original ICE 392)

Original: 392 (7×8×7) → Oracle: 294 (7×7×6) −98

The report claims snooze "reuses R-2 advance-warning scheduling logic." But R-2 hasn't shipped, and snooze is harder: where do you store snoozedUntil? In notification state (invisible in the note) or rewrite the file inline (new file-I/O capability with conflict risk)? The plugin currently never modifies vault files. Adding writes is a major expansion.

⚠️ Medium Severity Critiques

⚠️ Integration Complexity

S-1 — Webhook Relay Alternative (Original ICE 392)

Original: 392 (7×8×7) → Oracle: 224 (7×7×5) −168

"Replace hardcoded Telegram URL" sounds like a config change. It isn't. Discord wants {"content": "..."}, Slack wants {"text": "..."}, n8n wants raw POST body. The current template system ({taskName}, {deadline}) is string interpolation, not JSON. You need per-provider presets or a JSON body editor. Also: webhook URLs are secrets — do you mask them in logs like tokens?

⚠️ Parser Assumption

M-1 — Context-Rich Notifications (Original ICE 384)

Original: 384 (6×8×8) → Oracle: 288 (6×8×6) −96

"Extract 2–3 lines below the task" assumes the scanner has line-context awareness. The current VaultTask stores originalLine but not surrounding lines. You'd need to keep file handles open or parse entire files into arrays — non-trivial scanner refactoring.

⚠️ Underscored

A-2 — Priority Inbox Adaptation (Original ICE 180)

Original: 180 (6×5×6) → Oracle: 384 (8×8×6) +204

Buried because treated as unproven. Users already use frontmatter metadata (priority, due). The math is trivial: score = daysUntilDeadline * w1 + daysSinceModified * w2 + priorityValue * w3. Impact 6→8: transforms a flat dump into "do this first." Confidence 5→8: proven pattern in every email client, task manager, issue tracker. This should be Phase 2, not bottom of the heap.

⚠️ Solves Non-Problem

M-2 — Dynamic Check Cadence (Original ICE 216)

Original: 216 (6×6×6) → Oracle: 108 (6×4×5) −108

"Check every 5 min near deadlines" only matters while Obsidian is open — when users are actively working and least need aggressive checking. If Obsidian is closed, cadence is irrelevant. Adds interval recalculation complexity for cosmetic benefit. Defer or cut.

⚠️ Negative Value Risk

C-2 — Obsidian Reminders Plugin Bridge (Original ICE 210, Retained)

Should be Removed, not Retained. The Reminders plugin has no API stability guarantee. Format changes break your bridge for all users who enabled it. You're coupling reliability to a dependency you don't control. Better: make your own scanning fast enough that duplication doesn't matter.

⚠️ Slightly Optimistic on Ease

M-3 — Dedicated Sidebar View (Original ICE 448)

Original: 448 (8×8×7) → Oracle: 384 (8×8×6) −64

Strong idea. Custom views are a core Obsidian pattern and the click-to-scroll interaction transforms the plugin from background utility to visible workspace tool. However, Ease 7 → 6: click-to-scroll positioning in Obsidian's editor requires leaf.setEphemeralState({ line }) which has edge cases with folding, live preview, and Canvas notes. Also, the sidebar must stay in sync with the scanner's deduplication logic — a shared state layer is needed between notification engine and view.

⚠️ File-Write Risk

R-3 — Reminder-First Authoring (Original ICE 392)

Original: 392 (7×8×7) → Oracle: 336 (7×8×6) −56

Excellent for adoption — removes the need to learn task syntax. But Ease 7 → 6: writing to a user's file on their behalf needs conflict handling. What if the file is open and has unsaved changes? What if the destination path doesn't exist? The modal also needs a file picker (Obsidian's suggestModal for vault paths) which is straightforward but adds UI complexity. Still, this is a high-value onboarding feature that competitors lack.

Missing Risks Entirely

Testing
How do you test "notify 1 day before"? Mock system time? Wait 24 hours? Real engineering cost never budgeted.
State Migration
notifiedTasks format changes (E-2, R-2, A-1) need migration code. Old plugin data must load without crashing.
Feature Interaction
R-2 + E-2 + A-1 + M-2 creates a matrix. "I snoozed it, then the day changed — do I get another?" Each pair needs a rule.
Support Burden
Users will file "why didn't I get notified?" The answer: snooze + daily suppression + cadence all interacted opaquely.
Backward Compatibility
R-2 changes default behavior on upgrade. Users get new notification types without opting in. Default-off is safer.

✅ Build First: M-3 + A-2 + E-2

Three high-ICE ideas with low uncertainty and no hidden dependencies. The sidebar (M-3) gives users immediate visibility, Priority Inbox (A-2) gives them order, and duplicate suppression (E-2) stops the spam. Together they prove the plugin can get smarter without getting more complex.

⚡ Invest 2 Days: Prototype getUpdates

If desktop polling is negligible, you unlock C-1 (highest user-delight feature) and R-1. Do not dismiss based on theoretical mobile constraints.

🚫 Do Not Ship Together

R-2 + A-1 + E-2 + M-2 in one release creates support hell. Users won't understand why they did or didn't get notified. Either ship R-2 default-off, or ship A-1 first and gather feedback.
